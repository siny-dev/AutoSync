## Module version activation gate

The isolated module-chain smoke verifies initial resolution and data flow only. It does not test upgrading the AutoSync module while Workboard remains open. The earlier read-only audit found that engine_common_prepare() resolves the current AutoSync module path while engine_autosync_worker_ensure() leaves a live worker running. The latest Workboard source now compares the resolved module path with the live worker path, requests a graceful drain/reload, and starts the worker from the new verified path. This source behavior still lacks a native runtime acceptance test. An isolated resolver test using the current 5600G-installed engine/module first resolved AutoSync 0.1.0, then resolved a temporary 0.1.1 source pointer with verified=true while retaining both cache versions. This confirms next-resolve retrieval/verification, not activation of a running worker. Since AutoSync declares activation_mode=restart, a new package may be cached without replacing code already loaded in the running worker. Treat module fan-out to an already-running app as unverified until an acceptance test confirms a background-worker restart with the UI left open, durable outbox/state preserved, and no duplicate writes. A local smoke test confirmed that the same AutoSync 0.1.0 module can reopen a Workboard worker after one offline edit: one queued operation drained after server recovery and the peer received it. This did not simulate publishing a newer module or the parent app detecting and initiating the version-triggered worker restart.
Still required before claiming Workboard connected: define and provision per-PC adapter configuration and bootstrap modes, migrate persistent IDs in one canonical copy only, prepare H255 listener/TLS/app-scoped credentials, verify AutoSync module resolution on both hosts, and run the real two-PC pilot. Offline restart/replay and same-row concurrent-edit UX also need explicit acceptance coverage. Keep the legacy Sync writer disabled for these records during the pilot.
## Recommended data model

A guarded seeder is available at tools/seed_workboard_ids.py. It requires a separate destination, refuses to overwrite either source or destination, preserves UTF-8 BOM/line endings, and generates deterministic IDs for a migration copy. It was run against the current 18-row source into a temporary directory: the existing Workboard parser read 18 records (9 active, 9 completed) and 18 explicit IDs; removing only the inserted comment lines reproduced the source bytes exactly. The shared source SHA-256 remained 447decd84f31dc15a3930169a55450870527dda5c03689ab10b1bfe492846893. This proves only the seeder/parser compatibility, not AutoSync deployment or a production migration.

Use AutoSync as the sole live transport and give Workboard its own app_id: workboard namespace. Do not run the old Sync GitHub worker beside it.

After a reversible, isolated migration test, represent each task as one record keyed by its stable sync-id. Include the four cell values, active/completed section, and explicit position in the JSON payload. Keep document headings and non-task prose locally; the adapter must preserve them when it applies row changes. Use AutoSync server revisions and conditional writes, stable operation IDs, and tombstones for removal. Different task rows can then update independently, while concurrent edits to the same task are kept as a visible conflict.

## Safe rollout

1. Do not write to the production task list or use the production workboard namespace during a test. Make a copy in a temporary directory and confirm the adapter can parse and re-render every row without changing its text, section, or order.
2. On that copy, assign one stable ID per existing row. Verify 18 rows, 18 unique persisted IDs, identical four-cell values, and a byte-for-byte backup before/after comparison of all unrelated Markdown. Exercise edits, completion moves, duplicate-looking rows, deletion tombstones, and restart recovery.
3. Run two local adapter instances against a disposable AutoSync server and independent local Markdown copies. Test separate-row edits, same-row conflicts, offline queue/reconnect, duplicate acknowledgement, and restart. Confirm the legacy GitHub Sync worker stays disabled.
4. Before a real migration, preserve the current file byte-for-byte. Seed exactly one canonical copy, verify the remote row count and IDs, then bootstrap the other PC from that verified state. Never seed two diverged copies as separate initial truth.
5. Enable the AutoSync adapter only after the H255 TLS/service/client test and both PCs report the same record count and content hash. Keep the prior file and adapter rollback path until the user confirms the result.
